## 反馈代码中的已复现问题

来源：用户先前提供的附件
`/home/jo/.codex/attachments/505bed21-cc1d-4079-a7d2-81f2657e93d7/pasted-text.txt`。

`vision_link_send_feedback()` 第 116 行在栈上创建 `uint8_t frame[38]`，
第 159 行传给 `CDC_Transmit_FS()` 后返回，且未记录返回状态。

本机旧完整工程
`/home/jo/my-project/20.standard_robot_firmware_only_8f18d3c/20.standard_robot_firmware_only`
可确认其 USB 库的发送语义，但不能当作当前烧录工程：

- `Src/usbd_cdc_if.c:301`：忙时返回 USBD_BUSY，否则将调用者指针交给 USB 库。
- `Middlewares/ST/STM32_USB_Device_Library/Class/CDC/Src/usbd_cdc.c:830`：
  `USBD_CDC_SetTxBuffer` 仅保存指针，没有复制内容。
- 同文件第 865 行：发起传输时置 `TxState=1`；完成回调才清除忙状态。
- `Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_pcd.c:1798`：保存发送指针；
  后续 FIFO 中断路径 `PCD_WriteEmptyTxFifo` 才读取数据。

因此，在发送函数先返回、USB 后读取的时序下，栈数组已失效。
双向工作会改变调度和栈使用，可能使问题暴露，但没有实机证据证明本次就是该路径。
该缺陷可以造成数据损坏；不能从内存复现直接推导出 COM3 永久失效或描述符错误。

复现工具：`rm_serial_driver/tools/probe_feedback_buffer_lifetime.py`。
它原样编译提供的反馈 C 源码，以仅保存指针的内存 CDC 替身模拟延迟读取，
使用 GCC AddressSanitizer 检查；协议常量和硬件接口由测试桩提供。
结果：原函数触发 `stack-use-after-return`，定位到第 116 行的 `frame`；
独立的持久缓冲区、单一发送者对照正常读取 38 字节。
完整诊断输出：`frame_rate_diagnostics/com3_feedback_lifetime_20260923.json`。

```bash
python3 rm_serial_driver/tools/probe_feedback_buffer_lifetime.py \
  --source /home/jo/.codex/attachments/505bed21-cc1d-4079-a7d2-81f2657e93d7/pasted-text.txt \
  --output frame_rate_diagnostics/com3_feedback_lifetime_20260923.json
```

修复原则是由单一发送者持有持久缓冲区，传输完成前不修改，忙时跳过或排队最新反馈，
并记录 OK/BUSY/FAIL。不能仅给数组加 static 后仍在每次调用时无条件重写，
否则尚未完成的传输仍可能读到被修改的数据。
不能用强制清零 TxState 假装完成；也不能在 USB 中断里等待发送完成。

另一个待确认路径是：如果 TxState 因端点/回调问题一直没有清零，后续每次反馈会
返回 BUSY。现有反馈函数丢弃返回值，无法从主机区分这个情况与反馈任务不再运行。
这是观测缺口和诊断假设，尚非已证实的实机故障。

## 主机实现边界

Windows helper 在同一循环中写串口、读串口和发送本地时钟心跳。
设备写入阻塞会延迟该循环读取；设备 I/O 异常会退出 helper。
Python 侧使用最新待发指令和至多一条活动写请求，并拒绝过期目标。
本地写确认只代表 Windows 写操作返回，不是电控已解析或已执行的确认。

这种串行读写可能放大一次设备阻塞，但不能单独解释停止 helper 后，独立 Windows
读取仍为 0 字节。上位机日志也不能证明设备没有收到最后一条超时写请求。
现有资料不足以排除 USB 驱动、设备供电、接插件或电机运动引入的干扰。

必要的板侧记录为：反馈任务心跳、TX 尝试/OK/BUSY/FAIL/完成次数、
RX 命令计数和 USB 复位/断开事件。断流时通过调试器读取，避免仅依赖已中断的 USB。

| 断流时板侧状态 | 下一步定位 |
| --- | --- |
| 反馈任务心跳也停止 | 任务阻塞、异常、栈或调度问题 |
| 心跳继续，BUSY 增长、完成计数不动 | USB 发送端点、完成中断、发送并发 |
| MCU 发送完成计数继续增长，Windows 仍无数据 | 核查完成含义，再查 Windows 驱动/端点读链路 |
| USB 复位或断开事件出现 | 核查供电、线缆、接口及设备 USB 状态 |

后续实物对照应先保持电机失能，仅做已确认不会驱动电机的双向收发，
再与运动状态比较，才能把纯通信问题与运动相关干扰分开。
当前没有自动执行这一步，也没有要求用户重复三分钟运动测试。
