# 有目标视觉延迟对照结果（2026-09-22）

后续已实施进程分离，修复后的E/F复测见 [分离实施与对比](async_debug_split_2026-09-22.md)。本文件保留修改前A–D基线。

## 结论

当前 WSL/CycloneDDS 配置下，同步调试图生成与发布是实测到的明显瓶颈。关闭调试图时检测接近 30 FPS；原尺寸图接入一个 RViz 订阅后降到 15.97 FPS。只将最终显示图缩到 960x720，恢复到 22.47 FPS，尚不足以达到 30 FPS。

缩图提高吞吐、降低完整回调耗时和最长输出间隔，但检测消息年龄并未明显降低。不能把回调耗时下降等同于端到端延迟同比下降。

## 条件与方法

- 相机 MV-CS016-10UC，1440x1080 BayerRG8，设定 30 FPS，曝光 3000 us，增益 12 dB。
- 权重：`deployment/yolo_v8_gray140_candidate_20260826/model.pt`；部署身份 `armor_pose_real_blank_v1_candidate_20260812`。
- 实际后端 `cuda:0`，`fp16=false`。`imgsz=640`，`conf=0.40`，`normalized_dual_pnp_latch`，灰度 140。
- 相机输入与调试图发布 QoS 为 BEST_EFFORT、KEEP_LAST、depth=1。C 段实际查询确认 RViz 也为相同策略，唯一调试图订阅者为 RViz。
- 使用现有 `cyclonedds_wsl_local.xml`：MaxMessageSize=1400B，FragmentSize=1300B。结论限定于这一传输配置，不宣称所有 ROS/RViz 环境均有同等开销。
- COM3 由 Windows 接管，115200，`transport=windows`、`receive_only=true`。启动现有 gimbal TF 与 Tracker，未启动 Aimer、指令转发或双向发送。
- 装甲板固定在视野中，各段所有处理帧均有候选、有效 Armors；全部采样 Tracker 输出 tracking=true。
- 每段首次图像回调后预热 5 秒，正式窗口 30 秒，共 120 秒正式数据，20 秒预热，不含模型启动与阶段切换时间。四段共 2938 个有效检测样本。
- A：关闭调试图；B：原尺寸调试图、无订阅窗口；C：原尺寸调试图、一个 RViz；D：保持同一 RViz，仅最终调试图转成 960x720，INTER_AREA 缩放。
- D 只在独立计时脚本内缩图，不修改模型输入、PnP 坐标、相机内参或正式 YAML。
- 计时脚本包装原节点函数，以 perf_counter_ns 测调用墙钟耗时；逐帧保存在内存，结束后写 JSON。独立观察进程仅订阅 CameraInfo、Armors、Target、GimbalFeedback，不订阅大图。

## 检测内部耗时

每格为 平均 / P95 / 最大，单位 ms。模型调用包括其预处理、推理和后处理，不等于纯 GPU kernel 耗时。几何项是 `raw_track_latch.process_frame`，不是整个回调中所有非模型操作的总和。绘图项包装 `draw_raw_result`；图像拷贝、消息对象构造和其他未单列步骤计入完整回调。

| 操作 | A | B | C | D |
| --- | --- | --- | --- | --- |
| Bayer图像转换 | 0.83 / 1.15 / 1.64 | 0.89 / 1.49 / 3.34 | 0.88 / 1.24 / 4.80 | 1.55 / 2.65 / 5.79 |
| 模型predict调用 | 15.55 / 25.08 / 32.28 | 13.39 / 24.21 / 40.50 | 13.16 / 23.66 / 30.67 | 12.80 / 17.30 / 29.70 |
| 灯条与几何/PnP处理 | 0.72 / 0.97 / 7.13 | 0.64 / 0.92 / 4.92 | 0.67 / 0.99 / 6.52 | 0.65 / 0.96 / 6.84 |
| 画框 | 0 / 0 / 0 | 0.14 / 0.22 / 0.68 | 0.16 / 0.25 / 4.31 | 0.13 / 0.24 / 0.47 |
| 调试图转ROS消息（D含缩图） | 0 / 0 / 0 | 7.90 / 9.88 / 21.47 | 8.81 / 13.26 / 21.11 | 9.95 / 11.80 / 23.44 |
| 调试图publish调用 | 0 / 0 / 0 | 3.72 / 4.68 / 14.61 | 33.73 / 52.71 / 59.58 | 14.52 / 18.67 / 28.22 |

关键证据：接入 RViz 后 publish 调用平均由 3.72 ms 增至 33.73 ms。BEST_EFFORT 不保证 publish 立即返回；转换、序列化、DDS发送和调度工作仍可能同步占用调用线程。该计时没有继续拆解 DDS 内部，不能断言某个驱动或具体内核函数就是根因。

缩图后发布调用降低至 14.52 ms，但缩图与消息转换合计反而略增到 9.95 ms。这解释了为什么只缩图能改善、却不足以恢复 30 FPS。C 到 D 吞吐约提升 41%，完整回调平均耗时约下降 29%；这不是完整闭环延迟改善比例。

Armors 在调试图发布之前输出。因此一个回调末尾的调试图开销，主要延迟下一帧处理，不能将完整回调耗时直接当作本帧检测消息年龄。

匹配帧使用相同相机时间戳。这一到达差包含 TF 等待、Tracker计算、ROS调度和观察端误差，不是直接测得的纯 EKF 耗时，也未单独精确分离 TF 等待。

所有段的反馈 MCU 间隔均为 50 ms，说明本次提供的反馈约 20 Hz。不能由此推断电机内环也只有 20 Hz；也不能将其直接定为主要延迟原因。读取期间未出现持续反馈断流，最大接收间隔约 65 ms。

阶段间重启检测器导致 Tracker 的 max_dt 保护触发，发生在阶段切换/预热期间，未混入正式采样；不是本轮正式窗口中发生的随机串口故障。

## 边界与下一步

1. 本轮是单目标静止、无控制发送对照，不代表快速运动、多目标或比赛性能。仅各条件一段，不做统计显著性声明；模型调用本身在各段也有负载/调度波动。
2. ROS相机时间戳在SDK取帧之后生成，以上消息年龄不含之前曝光、USB与SDK等待；没有测出物理到屏幕的光学延迟。已确认 RViz 进程、图像订阅及 QoS，未以屏幕录像测量实际呈现时刻。
3. 本轮只接收，未复现或解决 Windows 双向发送确认超时，也未测试云台机械响应。不能用本轮连续反馈正常来判定双向发送已修好。
4. 优先将调试图的转换/发布从检测关键路径分离，并采用有界的最新帧机制；需要注意 Python GIL，不能仅加一个线程就承诺改善。可结合独立发布进程、降低显示刷新率、适当缩图，保持检测原始输入。下一步实施后用本轮 C/D 条件验证。
5. 当前不需要先训练新模型。FP16/TensorRT不是这次定位出的首要处理项。
