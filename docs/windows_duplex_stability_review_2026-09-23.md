# Windows 双向桥稳定性复核（2026-09-23）

> 本文保留修复前诊断证据。用户随后要求修理，主机代码已更新；最新进度和修复前后对照见
> [主机修复报告](windows_duplex_stability_fix_2026-09-23.md)。下文“生产代码未变”指诊断阶段。

## 结论与本轮范围

用户要求优先检查双向桥稳定性。这个方向仍未被排除：最近通过的实机基线运行的是
`transport=windows, receive_only=true`，发生故障时运行的是
`transport=windows_duplex, receive_only=false`。前者不能用作后者的稳定性验收。

本轮重新分析已有主机日志、独立 ROS 观察记录和服务启动参数；用户随后明确允许检查
本机主机桥与离线测试，已完成主机实现检查、故障注入和十分钟正常负载。
没有打开、修改电控源码，没有分析姿态数据，没有切换接收服务或向 COM3 发送数据。

已复现主机桥的两处稳定性缺口：同步写入拖住反馈/心跳，以及部分超时请求无法清理。
正常内存负载600.201秒、29268次写入均成功确认，未复现永久断流；
因此存在需要修正的主机实现问题，但实机永久断流的唯一原因仍未证明。

历史报告记载的主机内存对照为 60.105 秒、2921 条提交和成功写确认、2922 条反馈，
无超时。这仅覆盖当时内存负载下的 Python/C# 管道；报告明确未覆盖真实串口驱动、
USB 或完整 ROS 调度，也没有提供慢写入等故障条件下的耐久结果。

## 重新核对的证据

| 证据 | 结果 | 支持的判断与限制 |
| --- | --- | --- |
| 当前接收服务 ExecStart | `transport=windows`、`receive_only=true` | 近期模式切换只读基线与故障双向路径不同 |
| 0.5 度试次独立观察 | 718 帧，最大间隔 77.675217 ms，序号/MCU 步进异常均为 0 | 停发前没有逐渐变慢的迹象 |
| 同次写确认超时 | 最后反馈后 132.278638 ms | 写确认缺失与断流邻近；超时日志晚于最后反馈，无法证明写调用从何时开始阻塞 |
| 同次辅助进程关闭 | 最后反馈后 249.077638 ms，Windows IOException | 缺少失败调用的精确阶段，不能单凭总入口异常判定是读还是写失败 |
| 同次 COM3 重开 | 最后反馈后 1174.094638 ms | 只证明端口重开；历史记录显示反馈未恢复 |
| 1 度试次独立观察 | 699 帧，最大间隔 66.104086 ms，序号/MCU 步进异常均为 0 | 同样突然停发 |
| 同次命令拒绝 | 最后反馈后 97.771033 和 113.047033 ms | 没有前一试次的写确认超时或 I/O 错误记录，不能合并为同一已知故障 |
| 无保持试次停止后的诊断 | 15 秒记录内有 15 次慢 `read_serial`，751.578～1150.102 ms | 回调存在秒级耗时；缺少连接阶段标记，不能直接归因于串口读取本身 |

事件相对时间取独立观察的 `wall_ns` 与 journal 的 `__REALTIME_TIMESTAMP`；
帧间隔用观察者的 `mono_ns` 计算。上述超时顺序表示日志出现顺序，不表示内部故障因果顺序。

主机源码现已核实：`windows_duplex_helper.cs:103` 执行同步写入，随后才在同一循环
读取反馈（第111行）和更新心跳（第126行）。WSL 侧异步等待 ACK，
不代表 Windows 侧设备写入已经与读取隔离。另在 `serial_bridge_node.py:108`
确认，即使选择 `windows_duplex`，`receive_only=true` 仍构造 `WindowsSerialReader`。

另一方面，桥停止后 Windows 独立读取曾为零，说明仅有 ROS 发布阻塞不足以解释全部现象；
但这也不能排除桥的交互先触发了设备或驱动异常。此前无应用数据写入时也发生过停发，
因此不能断言所有事件均由持续发送引起。

## 验证设计

所有软件测试使用独立内存端点，保留真实 Python/C# helper 与管道；
不连接物理 COM3，不发布实机目标，不加载电控实现。

| 检查 | 条件 | 判定重点 |
| --- | --- | --- |
| 长时间双向负载 | 至少 10 分钟，约 50 Hz 写入，反馈独立按 20 Hz 产生 | TX 提交/完成/拒绝/超时，RX 连续性，ACK 延迟，反馈最大空窗，队列及资源是否增长 |
| 设备写调用阻塞 | 内存端点分别注入 50、150、500 ms 写延迟；反馈源继续运行 | 分清反馈源仍产出而 helper 未读取，检查心跳是否同步停止，延迟结束后能否恢复 |
| ACK 异常 | 分别延迟、丢弃确认，与设备写阻塞独立测试 | 接收是否继续，超时请求是否正确清理，迟到 ACK 是否误配新请求 |
| 管道与时钟扰动 | 管道分片、限时背压、心跳暂停及模拟时钟偏差 | 请求新鲜度、内存有界、恢复后无旧请求集中补发；不修改主机系统时钟 |
| 错误与恢复 | 模拟读错误、写错误、helper 退出和重复创建/关闭 | 错误阶段可辨认，无孤儿 helper、无资源持续泄漏，恢复后的接收和请求状态独立 |
| ROS 集成 | 同样的内存端点下运行节点回调与负载 | 读取/发送/健康检查是否互相阻塞，复现时可定位到具体阶段 |

记录应明确区分：提交请求、进入写调用、写调用返回、ACK 接收、Windows 读取、
WSL 接收、ROS 发布、连接开始/完成。Windows 写返回只代表主机写操作完成，
不能当作设备已解析或执行的确认。不同系统的单调时钟不直接相减计算单程延迟。

若离线复现，应先形成可重复失败用例，再在用户允许的主机代码范围内修复并复测。
若离线通过，仍不能宣布真实 USB 稳定；下一层才是核实双向桥可禁用发送后的实机接收对照，
以及满足既有实机条件的双向通信检查。必须先核实 `receive_only` 实际选择的路径，
防止名义上选择双向桥而仍执行另一条只读通路。

## 已执行的隔离测试

所有物理串口调用均由内存端点替代。新的端点由独立任务按 Windows 单调时钟每50 ms
产生38字节计数记录，内容仅为序号、生成时间、写尝试/完成次数及写调用时间，
不生成或解析机器人姿态。客户端按 WSL 单调时钟约50 Hz 提交不具备控制协议格式的
11字节测试数据。测试使用的 `COM999` 仅满足客户端名字校验，helper 入口只构造内存端点。

之前的内存测试端点每次 `Write` 才生成一帧反馈，因此无法验证“写被阻塞时，独立反馈源
继续产生数据但读取被拖住”的场景。新增端点补齐了这个覆盖缺口。

### 慢写入与设备异常

| 注入条件 | 主机反馈最大间隔 | 主机心跳最大间隔 | 结果 |
| --- | ---: | ---: | --- |
| 一次写入延迟50 ms | 86.144 ms | 77.775 ms | 恢复，170条成功 ACK，0超时 |
| 一次写入延迟150 ms | 167.370 ms | 167.372 ms | 恢复，164条成功 ACK，1条超时 |
| 一次写入延迟500 ms | 522.889 ms | 522.894 ms | 恢复，147条成功 ACK，1条超时 |
| 写调用按传入期限抛 TimeoutException | 终止前12条反馈 | helper退出 | 第5次写仅尝试未完成，端点生成15条记录，其中3条留在内存队列 |
| 写调用抛 IOException | helper退出 | helper退出 | 不误报该次写成功 |
| 读调用抛 IOException | helper退出 | helper退出 | 已返回的写 ACK 与随后读错误区分开 |

150/500 ms 用例刻意令内存写调用超过传入期限仍不返回，用于模拟底层阻塞；
不证明真实 SerialPort 在此次故障中确实超过期限。50 ms 用例的传入写期限为72 ms。
500 ms 用例中，生成到 Windows 读取的最大延迟为490.630 ms，且序号连续，
直接证明该注入条件下的停顿发生在 helper 读取阶段，结束后数据集中交付。

三种抛异常用例的工具退出码为1，表示故障成功暴露为连接级错误；
不是正常负载测试失败。它们也说明 `Windows serial write acknowledgement timed out`
与设备 `Write` 抛超时异常是不同路径：前者在 Python 层可只丢弃请求，后者会退出 helper，
接收也因此停止，需要节点重建连接。不能用“ACK 等待异步”推导设备写超时不影响接收。

### ACK 丢失、迟到及请求替换

这一组只使用真实 Python 客户端和合成进程管道对端，**不是**真实 Windows helper：

- 对端保持反馈和时钟消息，只丢弃20条 ACK：20条请求均按期限失败，接收继续；
  空闲0.5秒后 `expired_sequences` 与 `issued_sequences` 各留20条，随失败次数线性增长。
- 同样20条请求改为 ACK 延迟150 ms：请求先超时，迟到 ACK 到齐后两个集合均回到0。

源码中超时序号只在对应迟到 ACK 到达后清除，没有未到 ACK 的回收界限。
这暴露了长连接故障下的资源管理缺口，但20条记录并非资源耗尽，也未证明历史25～40秒
断流由此引起。不能将合成对端丢 ACK 当作真实本地管道已经丢字节的证据。

进一步用**真实 Windows helper**复核：将请求期限设为40 ms，同时令第5次内存写入
阻塞500 ms。共172次提交、149条成功 ACK、3条超时；结束时无待发/活动请求，
但 `expired_sequences` 和 `issued_sequences` 各残留2条。随后反馈和成功写入均已恢复，
helper 正常退出。这将残留问题从合成管道对端扩展到了真实 helper 路径。
实现中输入队列只有一个位置，满时直接移除旧请求（`windows_duplex_helper.cs:67`），
不会为被替换的请求发确认；客户端只等迟到 ACK 才清理的策略不能覆盖这种情况。
应区分“被替换而未执行”“写已开始但结果未知”和“过期拒绝”，不能笼统重试。

该结果仍是刻意超时的内存端点故障注入，不证明实机日志中已经发生相同替换过程。

### 错误后重建及已有回归

- 原有主机收发、时钟、ROS桥选择/调度等35项测试通过；未纳入另1项分段诊断工具测试。
- 新增3项真实 helper 内存测试通过：读错误、写错误、写超时分别使旧 helper 结束后，
  创建新 helper，先收到零写入的独立反馈，再成功完成新写入；旧请求未自动重放。
- 原有 ROS 双向内存集成中的节点自动重连测试通过。新增独立20 Hz反馈的十分钟负载
  已在传输层完成，不将它描述为十分钟完整 ROS 或物理 USB 验收。

本轮只新增诊断端点、探测工具和故障恢复测试，没有更改生产桥实现。
读写共用执行循环是已复现的耦合风险；永久断流仍未在内存对照中复现。
后续修复应优先隔离写入与读取/心跳的调度，明确设备写超时的处置及连接重建状态，
同时给超时序号跟踪增加边界。不能把未知结果的写请求重发，或把设备异常伪装成成功 ACK。

### 后续源码核对：恢复与并发修改的约束

再次核对当前主机实现后，确定修复时还需覆盖以下行为：

- `windows_duplex_helper.cs:44` 的管道帧由多次 `Write` 组成。若拆开读取和写入任务，
  各任务输出必须由单一输出者或整帧锁串行化，避免 ACK、反馈和心跳相互插入而损坏封装。
- `windows_duplex.py:222` 仅在迟到 ACK 到来时回收超时序号，
  而 helper 第67行替换队列请求时没有终止状态。应为未执行的被替换请求提供明确结果，
  同时处理对端不再回复的情况；仅对集合做简单清空会令迟到 ACK 被判为非法确认。
- `serial_bridge_node.py:160` 在读取回调内同步调用 `open_serial`；
  `close_serial` 也同步等待端口关闭。`windows_serial.py:140` 关闭时可以等待 helper 3秒。
  因此历史慢 `read_serial` 不能直接等同于底层串口读取慢，需将打开、关闭、实际读取分别计时。

这些是源码核对结果，不是新的实机复现，也没有据此修改生产桥或启动控制。

```bash
/usr/bin/python3 rm_serial_driver/tools/probe_windows_duplex_stability.py \
  --duration 600 --output frame_rate_diagnostics/duplex_nominal_new.json

  --duration 4 --fault slow_write --delay-ms 500 \
  --output frame_rate_diagnostics/duplex_slow500_new.json

  --mode lost --output frame_rate_diagnostics/duplex_ack_loss_new.json

  -q rm_serial_driver/test/test_windows_duplex_fault_recovery.py
```

输出文件要求不存在，避免覆盖既有记录。JSON包含实际计数和原始时间记录；
`records` 每行为：WSL到达时间、序号、Windows生成微秒、写尝试数、写完成数、
最近写开始/结束微秒、Windows读取结束微秒。
