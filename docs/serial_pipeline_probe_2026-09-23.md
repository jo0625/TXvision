## 结论与当前状态

已在第二轮有效实机采集中复现 4 次约 2.5 秒空窗，并定位到通信桥定时器使用 ROS/系统时钟：
系统时钟向后跳变时，读取定时器暂停，Windows 已经收到的反馈在途中积压，定时器恢复后集中交付。
Windows 读取、Linux 主机线程、ROS 发布函数本身没有对应的秒级停顿。

`serial_bridge_node.py` 的读取、发送、健康检查、状态重发四个定时器已改用
`ClockType.STEADY_TIME`，消息 header 仍使用原来的 ROS 时钟。

## 根因证据

第二轮稳定分析区间约 118 秒，Windows/WSL/ROS 三段匹配到 2171 帧。
下表时间从分析区间起点计算；回拨幅度为 REALTIME 增量相对 MONOTONIC 增量的差值。

| 时刻 / s | 系统时钟回拨 / ms | 读取定时器停顿 / ms |
| --- | ---: | ---: |
| 3.93 | 2459.0 | 2461.6 |
| 36.25 | 2488.6 | 2490.6 |
| 68.49 | 2618.1 | 2622.1 |
| 100.73 | 2482.7 | 2485.1 |

四次时钟回拨与定时器停顿一一对应，误差约数毫秒。
桥接进程中的独立单调时钟心跳在这些时刻持续运行，排除了整个桥接进程停跑 2.5 秒的解释。

| 位置 | 本轮最大值 |
| --- | ---: |
| Windows 收到相邻反馈的间隔 | 87.1 ms |
| WSL 解包相邻反馈的间隔 | 2634.1 ms |
| 独立 ROS 观察者收到反馈的间隔 | 2638.6 ms |
| 稳定运行阶段一次 read_serial 调用耗时 | 30.2 ms |
| 单帧 ROS 发布调用耗时 | 5.57 ms |
| ROS 发布开始至独立观察者收到 | 6.86 ms |

通俗解释：原定时器根据“现在几点”安排下次读串口。
时钟被拨回约 2.5 秒后，程序要等时钟重新走到原先的触发点，期间不会按原周期读取。
单调时钟用于计算经过了多久，不会因为系统日期时间的校正而倒退。

本次定位的是通信桥对系统校时的敏感性，没有定位是谁触发系统校时，
也没有全局更改 Windows/WSL 校时服务。其他节点的时间戳与定时器需要按实际影响另行判断。

## 目的与实施

针对之前约 2.51 秒的反馈到达空窗，增加以下计时：

1. Windows 辅助程序完成串口读取的前后时刻。
2. WSL 解开对应字节块的时刻，按反馈序号关联。
3. ROS 发布反馈的前后时刻。
4. 独立 ROS 观察进程收到反馈的时刻。

同时记录通信桥回调耗时、读取定时器间隔、Windows 心跳、Linux 线程心跳和检测消息。
诊断程序保留原来的 windows_duplex 接收通路，但忽略所有角度指令，发送定时器不执行写入。
本次没有启用云台跟随或发送电机目标。

## 计时边界

Windows 与 WSL 的时钟起点不同，不直接相减声称得到绝对单程传输延迟。
使用各自时钟的相邻帧间隔，以及同一 WSL 单调时钟上的解包、发布和订阅时刻定位停顿。
记录还包含 MONOTONIC、MONOTONIC_RAW 与 REALTIME，保留时钟跨度差异供复核。
单独的 Windows 心跳不能证明 USB 下位机正在反馈。
