## 范围与边界

本轮只使用既有实测记录、主机日志和 Windows 即时设备状态。
没有打开、检索、解压、分析或修改任何未开源电控源码及固件包；
没有打开 COM3、发送控制指令或启动云台运动。

## 当前结论

三轮动态跟随的反馈都不是逐渐变慢或逐步丢帧，而是在正常连续到达后突然永久停止。
0、0.5、1 度保持设置均出现相同的“突然停止”形态，因此角度保持阈值不是根因。

当前主机上没有串口桥或动态跟随进程运行，Windows 也没有枚举出 COM3：

- 旧 `USB\VID_0483&PID_5740` 记录为未连接，Problem 45。
- 当前总线 6-2 为 `USB\VID_0000&PID_0002`，设备描述符请求失败，Problem 43。
- `Win32_SerialPort` 当前没有返回串口。

这表示当前阻碍发生在 USB 枚举阶段，早于 COM 端口、ROS 和应用协议。
但设备可能处于断电、拔线或异常供电状态，所以当前状态不能单独证明此前三轮故障的唯一原因。

## 0.5 度试次的故障顺序

绝对时间使用独立观察与 systemd 日志中的主机时间：

| 事件 | UTC 时间 | 相对最后反馈 |
| --- | --- | ---: |
| 最后一帧反馈 | 08:35:58.649846 | 0 ms |
| 写确认超时 | 08:35:58.782124 | +132.278 ms |
| Windows 串口管道关闭并报告设备 I/O 异常 | 08:35:58.898924 | +249.078 ms |

更早在 08:35:50.445 出现过一次过期命令拒绝，但反馈随后又连续运行约 8.2 秒。
所以单次过期拒绝不是这次永久断流的直接触发条件。

最后反馈、写确认超时和设备 I/O 异常在约 250 ms 内连续出现，说明此次故障同时影响读写，
优先级高于单纯的 ROS 订阅、网页显示或反馈解析问题。重新打开端口后仍无反馈，
也说明“进程重连成功”不等于设备通信恢复。

## 1 度试次的故障顺序

| 事件 | UTC 时间 | 相对最后反馈 |
| --- | --- | ---: |
| 最后一帧反馈 | 08:49:50.141734 | 0 ms |
| Windows 拒绝过期命令 | 08:49:50.239506 | +97.772 ms |
| Windows 再次拒绝过期命令 | 08:49:50.254781 | +113.047 ms |

该轮没有记录到设备 I/O 异常。停止双向桥后，Windows 可以打开 COM3，
但 3.064 秒读取到 0 字节。它与 0.5 度试次不是完全相同的外部表现：

- 0.5 度试次表现为端口 I/O 失败。
- 1 度试次表现为端口仍可打开，但反馈源不再产生可读数据。

因此目前不应强行用单一主机错误解释三轮故障。

## 与只读基线的对照

单调时钟修复后的只读实机基线持续约 118.35 秒，匹配 2457 帧反馈，
最大到达间隔 64.5 ms，没有超过 150 ms 的空窗。该轮没有发送控制角度。

三轮主动测试都在约 25.5 至 40.7 秒后停止反馈。现有证据只说明故障与主动测试条件相关，
还不能区分以下因素：

1. 双向 USB 写入负载。
2. 电机使能和运动产生的供电波动、电磁干扰或接插件扰动。
3. 设备内部反馈任务或 USB 端点状态变化。
4. Windows USB/串口驱动在设备异常后的不同恢复行为。

主机时钟回拨造成的 2.5 秒积压是已单独定位并修复的问题；
它不会造成当前的设备描述符失败，也不能解释停止后 Windows 独立读取 0 字节。

## 当前优先级

1. **已确认发生过 USB 枚举失败。** 完全重启后已经恢复，但复发时任何 ROS 或协议层测试都无效。
2. **较强证据：至少一次故障影响整个串口设备读写。** 0.5 度试次有 Windows 设备 I/O 异常。
3. **尚未区分：设备停止反馈与 USB IN 路径停滞。** 1 度试次端口可开但无数据。
4. **不支持：角度保持阈值导致断流。** 三种阈值都失败，保持期间仍按原频率发送。
5. **不支持：故障前 ROS 队列逐渐堆积。** 最后一帧仍新鲜，间隔没有恶化趋势。

## 后续黑盒步骤

所有步骤都不需要查看未开源代码：

1. 先由用户确认设备已上电并重新连接，只检查是否恢复 `0483:5740` 和 COM3；不打开串口。
2. COM3 恢复后，先做不少于三分钟的只读反馈基线，不发送任何控制指令。
3. 如果只读稳定，再由电控负责人确保电机硬件失能，在不可能驱动云台的条件下做双向通信负载测试。
4. 只有“电机失能双向稳定、使能后失败”时，才把供电、干扰或运动条件提升为主要方向。
5. 如果电机失能时双向仍失败，应记录故障后的 Windows PnP 状态、端口能否打开、读取字节数，
   并由电控负责人提供与实现无关的板侧心跳和 USB 状态计数。

当时停在第 1 步；后续恢复和只读基线结果见下文更新。

## 重新连接复查

用户回复“已重新连接”后，只查询 Windows PnP、串口枚举和本机进程，未打开串口：

- `Win32_SerialPort` 仍没有返回任何串口，COM3 未恢复。
- 6-2 仍为 `USB\VID_0000&PID_0002`，设备描述符请求失败，Problem 43。
- 未发现 `serial_bridge`、动态跟随记录器或 Windows 串口辅助进程占用设备。

因此，单次重新连接没有恢复 USB 枚举，软件占用也不是当前阻碍。
下一步应让下位机主电源完全断电后重新上电，再更换 USB 口或已知正常的数据线复查；
在恢复为 `0483:5740` 和 COM3 前，不打开串口、不运行 ROS 通信测试。

## 完全重启后的只读基线

用户再次完成连接后，Windows 已恢复正确枚举：

- 总线 6-2 为 `0483:5740`，COM3 状态 OK、Problem 0。
- 已有接收服务以 `receive_only=true` 打开 COM3；本轮没有另开串口。
- ROS 图中只有反馈、IMU和状态话题，没有目标角输入话题。
- 测量结束时 `command_active=false`。

最初使用 `ros2 topic hz --wall-time` 时，每约32秒显示一次约1.5秒间隔。

## 切换遥控模式后的只读观察

用户将机器人切换为遥控模式后，没有启动任何发送端，只读状态如下：

- 接收节点仍为 `receive_only=true`，`command_active=false`。
- ROS 状态为 `connected=true`，Windows 中 COM3 仍为 OK。
- `feedback_alive=false`，先观察8秒、随后再观察15秒，均未收到新反馈。

这与之前的设备I/O异常不同：本次端口仍连接，但遥控模式下反馈停止。
现有黑盒证据只能说明反馈停发与模式切换同时发生，不能在不查看未开源实现的情况下
认定它是固件设计行为或新的故障。

遥控模式不等于电机硬件失能，而且当前没有反馈可用于双向耐久判定，
所以不能在该状态启动步骤3。需要一种经过电控负责人确认的安全条件：
保持控制板、USB和周期反馈运行，同时从硬件上保证云台电机不可能动作。

## 切回视觉模式及 Windows 直读

用户切回视觉模式后，电脑仍保持只读：

- 10秒内没有收到反馈，`feedback_alive=false`。
- COM3 保持状态 OK，`connected=true`，`command_active=false`。
- 再停止只读接收服务，由 Windows 独立打开 COM3 读取 5.069885 秒。
- COM3 打开成功，但读取到 **0 字节**，没有执行任何写操作。
- 随后已恢复原接收服务，参数仍为 `receive_only=true`；结果仍为连接成功但无反馈。

本次序列提供了新的关键证据：

1. 视觉模式下只读反馈先稳定运行约三分钟。
2. 切换到遥控模式后反馈停止。
3. 切回视觉模式后反馈没有恢复。
4. 整个过程中没有向设备写入控制数据。
5. Windows 可以打开端口，但原始读取同样为0字节。

因此，**双向发令不是反馈停发的必要条件**。本次停发发生在字节到达 Windows 之前，
优先考虑模式切换相关的板侧反馈状态、USB IN 传输状态或设备状态机；
在不查看未开源实现的边界下，不能继续细分或声称已找到唯一内部根因。

后续不再优先执行双向负载测试。更有信息量的黑盒步骤是：完全重启恢复反馈后，
在电脑始终只读的条件下，对模式6到遥控模式的切换做一次明确计时，检查是否稳定复现停发；
如果复现，再完全重启并只保持模式6，确认反馈继续稳定。该对照不需要任何电脑端写入。

在没有电机硬件失能确认前，仍不进行双向发令或运动复现。

## 双向桥验证覆盖修正

用户提出优先检查双向桥后，重新核对服务参数：上述重启后的只读基线使用
`transport=windows, receive_only=true`，故障试次则使用
`transport=windows_duplex, receive_only=false`。这些基线不能证明双向桥稳定，
更不能排除其写入、ACK、管道或异常恢复路径触发故障。

此前“无应用写入也发生过停发”的事实仍保留；它只说明持续发送并非所有停发的必要条件，
不足以排除双向桥是另一些故障的触发因素。接下来优先做主机桥专项检查，
具体日志证据和待执行的离线故障注入条件见
[双向桥稳定性复核](windows_duplex_stability_review_2026-09-23.md)。本次未切换服务或发送实机指令。

用户允许检查本机主机桥后，专项已完成：真实Windows helper的内存双向正常负载
持续600.201秒，29268次提交全部成功确认，12451条独立反馈、0序号跳变；
最大接收间隔78.821 ms。故障注入则复现了写阻塞拖住读取/心跳，以及超时请求记录残留。
38项相关主机测试通过，未修改生产桥代码或重现实机永久断流。
当前应优先处理上述主机问题，而不是用只读基线排除双向桥。
