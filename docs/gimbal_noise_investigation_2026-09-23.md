# 云台异响离线排查（2026-09-23）

## 结论

最强证据指向：本轮错误的零角度指令被转发，随后即使没有新的视觉目标，pitch 反馈仍在
零位附近持续往复，直到电机失能后才稳定。用户也明确确认“停止移动或移开后仍持续，失能后才停”。

已经证实的是错误转发、停令后的反馈往复和失能后的稳定；尚未证实的是电机电流及内环的
具体成因。因此，“错误回零可能触发了保持目标时的振荡”是目前最有证据的因果假设，
不是已经确认某个 PID 参数错误。半径约束修复改善断跟，不能替代本次异响原因的判定。

本轮仅检查现有文件并生成离线报告，没有连接机器人、发送指令、修改或烧录电控固件。

## 为什么之前没有出现同样情况

比较此前 180 秒测试的有效控制段和异常 30 秒测试：

| 项目 | 前次有效控制段 | 异常本轮 |
| --- | ---: | ---: |
| 零角度载荷与旧 candidate 状态同时出现 | 33 次 | 7 次 |
| 这些零角度载荷通过 0.6 rad 角度差检查 | 0 次 | 7 次 |
| 实际转发到串口桥的零角度目标 | 0 次 | 7 次 |

前次这些消息到达时，零目标与 yaw 反馈的最短角距离约 161.7 至 179.9 度，
大于 0.6 rad（约 34.4 度），因此即使状态文本滞后，也被角度差检查挡住。
本轮对应角距离约 1.0 至 16.9 度，进入允许范围，使此前已存在的有效性错误暴露出来。
部分前次消息还会被反馈新鲜度检查拒绝，但所有 33 条均不满足 yaw 角度门限。

这里比较的是云台 yaw 的反馈坐标值，可能受上电参考零点等条件影响，
不代表用户旋转了装甲板，也不能直接推断两次机器人实际朝向相差 180 度。

无效零角度误转发已在此前修复：以同一条消息的 valid 为准，诊断状态文本不再决定是否发令。
这不是禁止合法的零角度目标，而是禁止失效消息变成回零指令。

## 异常本轮的时间线

时间均相对于记录开始，采用主机收到消息的单调时间：

| 时刻 | 记录证据 |
| --- | --- |
| 1.647 s | 目标 yaw 从约 -17.16 度跳到 0 度，两条指令相隔约 43 ms |
| 12.507 s | 最后一条转发目标为 yaw=0、pitch=0 |
| 12.525 s | 串口桥报告 command_active=true；这不是带 MCU 序号的接收确认 |
| 12.543 s | command_active=false，后续周期状态始终为 false |
| 13 至 17 s | 没有新转发目标，preview 状态为 invalid_input_command，pitch 反馈仍持续往复 |
| 19.002 s | 反馈模式从 6 变成 0 |
| 19.5 至 29.9 s | pitch 反馈固定约 0.08789 度，往复变化消失 |

停令后 13 至 17 秒共 78 个反馈样本：

- pitch 范围约 -0.747 至 +1.099 度，峰峰值约 1.846 度。
- 相邻反馈角度变化绝对值的中位数约 1.230 度。
- 76 对相邻变化中，有 62 对发生方向交替，且两次变化均至少 0.2 度。
- 这段相邻 MCU 时间戳严格相差 50 ms，避免把主机批量到达当成真实高速运动。
- 失能后的 204 个反馈样本 pitch 完全一致。

反馈只有 20 Hz，不能据此推算真实振荡频率，也不能排除高频变化的采样混叠。
这些是控制器报告的角度，不是独立的高速运动测量；但与用户听到的持续异响、失能后停止相符。

## 下位机行为与提供的源码不一致

提供的 `/mnt/e/000workplace-E/rm/rm视觉/串口协议/vision_aim(1).h`
定义 VISION_AIM_TIMEOUT_MS=200。
`gimbal_behaviour(1).c` 第 369 行附近写明：视觉超时后从模式 6 退回模式 3。

实际记录中，最后转发指令后的约 6.5 秒仍报告模式 6，然后由用户失能变成模式 0。
因此不能依据这份片段断言实际机器人已执行 200 ms 超时退出。
需要核对当前烧录版本的实际收包计时、vision_aim_online、模式选择及模式反馈字段来源。
记录没有 MCU 收包计数和最后收包时刻，尚不能区分超时逻辑未生效、其他代码刷新计时、
模式遥测与真实状态不同等具体原因。

上位机当前协议只有 11 字节角度帧，没有失能或停止字段。
收到 valid=false 时串口桥停止提交新目标并取消未发送请求，不会向机器人发送电机失能指令。
Windows 辅助进程没有在无新请求时自主重发角度的逻辑；20 ms 时钟消息只回传到 WSL，不写到 COM。
已经在途的请求无法靠取消本地队列撤回，因此不能把 ROS 停令时刻当成 MCU 的精确停收时刻。
